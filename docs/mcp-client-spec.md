## 3. Architecture Decision

### 3.1 Chosen model

V2 freezes one Provider-independent stable search/call gateway:

```text
explicit MCP config
  -> session startup and eager tools/list discovery
  -> immutable MCP catalog and remote invocation bindings
  -> register two stable native Harness adapters
       mcp_tool_search
       mcp_tool_call
  -> Provider tools[] contains only the phase-allowed gateway schemas
  -> individual remote MCP schemas never enter base Provider tools[]
```

The model discovers a remote tool with `mcp_tool_search`, receives a bounded ordinary ToolResult
containing its canonical identity and input schema, and invokes it with:

```json
{
  "tool": "mcp__server__remote_tool",
  "arguments": {"remote": "arguments"}
}
```

`mcp_tool_call` resolves the exact catalog entry and delegates to its existing `MCPTool` binding.
The call remains one ordinary `ToolExecutor` execution and therefore crosses the existing Plan
gate, validation hook, Permission gate, post-tool hooks, Artifact path, and CMV3 admission path
exactly once.

### 3.2 Rejected Provider-native option

Provider-native deferred loading is not a V2 production path. The current Harness cannot prove
all configured Providers can:

1. accept deferred tool definitions;
2. load a definition from tail state without rebuilding the base `tools` array;
3. authorize a later call to that loaded definition;
4. preserve the prior Provider prefix; and
5. express and parse the complete protocol through the current `ModelClient`.

V2 MUST NOT inspect Provider identity or capability at runtime. It MUST NOT implement a native
deferred path, a gateway fallback, or a compatibility mode.

### 3.3 Core requirements

- **MCPV2-ARC-001**: Runtime registration and Provider-visible schema exposure MUST be independent
  concepts.
- **MCPV2-ARC-002**: V2 MUST implement only the fixed `mcp_tool_search` plus `mcp_tool_call`
  gateway model in section 3.1.
- **MCPV2-ARC-003**: Individual remote MCP tool schemas MUST NOT be registered as direct
  `ToolRegistry` tools or serialized into base Provider `tools[]`.
- **MCPV2-ARC-004**: `MCPRuntime` MUST remain the sole MCP lifecycle owner; no additional MCP
  executor, registry service, policy layer, manager hierarchy, or persistence layer is allowed.
- **MCPV2-ARC-005**: The existing `ToolRegistry`, `BaseTool`, `ToolExecutor`, Plan gate,
  `PermissionGate`, post-tool hooks, ArtifactStore, and CMV3 pipeline MUST remain the only host
  execution path.
- **MCPV2-ARC-006**: There is no v1 direct-exposure fallback, Provider detection, feature flag,
  compatibility alias, or alternate tool-loading strategy.
- **MCPV2-ARC-007**: New MCP-specific production modules beyond the four paths in section 3.4
  MUST NOT be added.

### 3.4 Frozen module placement

MCP-specific production code remains limited to the four v1 modules:

```text
src/runtime/mcp/__init__.py
src/runtime/mcp/config.py
src/runtime/mcp/runtime.py
src/tools/mcp_tool.py
```

V2 adds no production module. Small integration changes are limited further by the exact table in
section 16.

## 4. Goals and Non-Goals

### 4.1 Goals

- Bound the MCP contribution to the Provider-visible base tool schema independently of the
  number of discovered remote tools.
- Keep the base tool representation deterministic throughout a stable Plan phase and same-turn
  continuations.
- Let Planning inspect immutable MCP capability metadata without making remote calls.
- Keep real remote calls under existing Plan and Permission semantics.
- Reuse all stable v1 config, transport, lifecycle, naming, result, failure, and CMV3 behavior.

### 4.2 Non-goals

V2 does not add:

- Provider-native deferred loading, Provider tool search, or Provider-specific branches;
- lazy MCP server startup, dynamic discovery, `tools/list_changed`, or hot reload;
- per-turn tool subsets, intent prediction, LRU, TTL, reuse scoring, semantic scoring, or dynamic
  unloading;
- embeddings, vector search, LLM reranking, hybrid search, or a search dependency;
- enabled/disabled tool configuration or exposure-surface configuration;
- an MCP executor, permission layer, Context layer, registry service, or cache manager;
- schema validation, argument coercion, repair, fuzzy resolution, aliases, or nearest-tool calls;
- Code Mode, Sub-Agent MCP sharing, Resources, Prompts, Apps, Tasks, Roots, Sampling, OAuth,
  credentials, or server hosting.

## 6. Exposure Model and Sets

### 6.1 Normative exposure states

The terms below describe observable state; they do not require a new policy manager or persisted
state machine.

- **DIRECT**: the Harness tool schema is included in the current Provider `tools[]` and the tool
  can be resolved through `ToolRegistry` in the current Plan phase.
- **DEFERRED**: a remote MCP binding exists in the immutable catalog and is searchable, but its
  own schema is never included in base Provider `tools[]`.
- **HIDDEN**: the tool or gateway is not model-visible or callable in the current Plan phase.

V2 MUST NOT add Codex-only model/code-mode variants.

### 6.2 Three distinct sets

1. **Registered MCP Tools** are validated remote bindings in `MCPRuntime`'s immutable catalog.
2. **Searchable MCP Tools** are registered catalog entries queryable through the currently
   available `mcp_tool_search` gateway.
3. **Direct Provider Tools** are ordinary `ToolRegistry` schemas serialized into Provider
   `tools[]`. For MCP, this set contains only phase-allowed gateways.

Membership in the registered set never implies direct Provider exposure.

### 6.3 Requirements

- **MCPV2-EXP-001**: Every valid discovered remote tool MUST become one registered immutable
  catalog binding.
- **MCPV2-EXP-002**: Every registered binding MUST be searchable when `mcp_tool_search` is direct.
- **MCPV2-EXP-003**: A registered remote binding MUST remain deferred for the entire session; a
  search or call MUST NOT make its individual schema direct.
- **MCPV2-EXP-004**: Gateway visibility MUST be derived only from existing Plan capabilities;
  exposure state, age, score, and per-turn prediction MUST NOT be persisted.
- **MCPV2-EXP-005**: Awaiting-approval, completed, and cancelled phases MUST hide both MCP
  gateways. Completed continues to expose zero tools.

## 7. Stable V1 Foundation

### 7.1 Dependency and activation

The official `mcp>=2.0,<3` package, SDK `Client`, automatic protocol negotiation,
`input_required_max_rounds=0`, and `cache=None` remain frozen. MCP is disabled by default and is
enabled only by explicit `--mcp-config <path>` host input.

The exact config remains:

```json
{
  "mcpServers": {
    "local_tools": {
      "type": "stdio",
      "command": "python",
      "args": ["path/to/server.py"]
    },
    "remote_tools": {
      "type": "http",
      "url": "http://127.0.0.1:8765/mcp"
    }
  }

```

Root, server objects, strings, URLs, duplicate keys, and unknown fields remain strictly
validated. Stdio `env`, HTTP headers/auth, interpolation, shell execution, config discovery, and
full Harness environment copying remain forbidden.

- **MCPV2-CFG-001**: MCP activation MUST remain explicit and disabled when
  `mcp_config_path is None`.
- **MCPV2-CFG-002**: V2 MUST add no config field or CLI option beyond the v1
  `mcp_config_path`/`--mcp-config` surface.
- **MCPV2-CFG-003**: The v1 strict config schema, host-config non-emission rules, `env` rejection,
  and protected `.mcp.json` behavior MUST remain unchanged.
- **MCPV2-CFG-004**: With no config, an MCP thread, event loop, subprocess, HTTP client, catalog,
  or gateway registration MUST NOT exist; native tool ordering and schemas MUST remain unchanged.

### 7.2 Transport and timeout

Stdio retains the exact SDK path:

```python
parameters = StdioServerParameters(command=server.command, args=server.args)
transport = stdio_client(parameters)
client = Client(
    transport,

Bare Streamable HTTP retains:

```

- **MCPV2-TRAN-001**: Only stdio and bare Streamable HTTP are supported; legacy SSE and custom

- **MCPV2-TRAN-002**: Every SDK Client MUST retain the single internal 120-second request timeout

- **MCPV2-TRAN-003**: Retry, reconnect, restart, alternate transport, and server-health state

- **MCPV2-TRAN-004**: The SDK owns framing, negotiation, process cleanup, and HTTP behavior; V2

### 7.3 Lifecycle

`build_agent_runner` and `build_runtime` construct only a dormant `MCPRuntime`. After a valid
`AgentContext` exists, `MCPRuntime.start()` enters one worker/event loop/supervisor, connects all
configured servers, exhausts discovery, constructs the immutable catalog and search index,
preflights collisions, registers the two gateways atomically, emits direct trace events, and
returns before the first Provider request.

Interactive mode reuses the same runtime and entered SDK Client contexts across tasks. The same
stdio child remains alive; Streamable HTTP does not promise socket or protocol-session identity.
`finish()` closes once before STOP reporting.

- **MCPV2-LIFE-001**: Deferred exposure MUST NOT defer server startup or discovery.
- **MCPV2-LIFE-002**: Catalog and gateway registration MUST complete atomically before the first
  Provider request.
- **MCPV2-LIFE-003**: The v1 dormant construction, sole async owner, session reuse, direct startup
  tracing, startup cleanup, and once-only shutdown contracts MUST remain unchanged.
- **MCPV2-LIFE-004**: Startup failure MUST leave no committed catalog, gateway registration,
  worker, child process, open Client context, or Provider request.

## 8. Immutable MCP Catalog

### 8.1 Construction

For each server, the runtime exhausts `tools/list` pagination, rejects repeated cursors and
duplicate remote names, validates names and schemas, and sorts entries by
`(server_id, remote_tool_name)`. It then builds one immutable tuple of entries and their lexical
search fields. The tuple is assigned only after all servers, schemas, identities, native
collisions, and gateway collisions pass preflight.

The catalog is built once per started session. It is never rebuilt per model call, per task, per
search, or per remote invocation. There is no `McpHandlerCache`, `ToolSearchCache`, or additional
catalog manager.

### 8.2 Catalog entry

Each entry contains exactly the runtime data already required to search or invoke:

```text
canonical_tool_id
server_id
remote_tool_name
description
input_schema
remote MCPTool binding
precomputed lexical token sets
```

Raw server/tool identity remains separate from canonical identity. The canonical identity stays:

```text
mcp__<server_id>__<remote_tool_name>
```

The v1 component rules, `__` prohibition, 64-character aggregate maximum, case sensitivity,
fail-fast collision behavior, and no-rewrite rule remain unchanged. The two gateway names must
also be absent from the native registry before atomic gateway registration.

Input schema validation remains limited to JSON-object shape and JSON serializability. The
Harness does not prove full JSON Schema validity. The effective description remains the remote
non-empty description or `MCP tool <server_id>/<remote_tool_name>.`. Titles, annotations, output
schemas, icons, raw protocol metadata, and connection data are not catalog-search output.

### 8.3 Requirements

- **MCPV2-CAT-001**: Discovery MUST exhaust every page exactly once and build one immutable,
  deterministically ordered catalog before first Provider use.
- **MCPV2-CAT-002**: Catalog identity and schema validation MUST retain the exact v1 fail-fast
  contract; sanitization, hashing, truncation, aliasing, or silent dropping is forbidden.
- **MCPV2-CAT-003**: Dynamic list notifications, rediscovery, hot reload, catalog mutation, and
  per-task rebuilding are forbidden.
- **MCPV2-CAT-004**: Search fields MUST be computed once at catalog construction and reused
  without a separate cache class.
- **MCPV2-CAT-005**: MCP annotations MUST remain untrusted and MUST NOT affect catalog exposure,
  ranking, Plan policy, permission, or operation classification.
- **MCPV2-CAT-006**: Full remote schemas MUST remain available in immutable catalog entries for
  search results and server-authoritative calls, but MUST NOT become direct Provider schemas.

## 9. Deterministic MCP Tool Search

### 9.1 Direct tool contract

The direct Harness tool is named `mcp_tool_search`. Its exact schema is:

```json
{
  "type": "object",
  "properties": {
    "query": {"type": "string", "minLength": 1, "maxLength": 256},
    "limit": {"type": "integer", "minimum": 1, "maximum": 10, "default": 5}
  },
  "required": ["query"],
  "additionalProperties": false
}
```

The tool overrides `validate()` only for this exact host gateway contract. It rejects unknown
arguments, a non-string/empty/over-256 query, a boolean/non-integer limit, and limits outside
`1..10`. It does not implement general JSON Schema validation.

The tool reads only startup-discovered in-process metadata. It performs no remote MCP request,
network I/O, server startup, repository I/O, catalog mutation, or schema exposure mutation.
Its operation is fixed as local read-only metadata discovery:

```text
kind: mcp.search
action: search
subject: mcp_catalog
scope_key: mcp:catalog:search
is_read_only: true
is_destructive: false
is_sensitive: false
```

### 9.2 Indexed fields and normalization

Only these fields are indexed:

- server identifier;
- remote tool name;
- description;
- top-level `input_schema.properties` names.

Titles and the remainder of raw JSON Schema are not indexed.

Normalization is fixed:

1. apply Unicode NFKC;
2. apply Unicode `casefold()`;
3. replace each maximal run of non-alphanumeric characters with one ASCII space;
4. split on whitespace;
5. discard empty terms;
6. de-duplicate query terms while preserving first occurrence.

A query with no normalized term fails validation.

### 9.3 Ranking

For each candidate, precomputed field terms are sets. Score the candidate once per distinct query
term:

```text
+16 when the term is in remote-tool-name terms
+8  when the term is in server-id terms
+4  when the term is in top-level property-name terms
+1  when the term is in description terms
```

Then add:

```text
+128 when stripped case-folded query equals canonical_tool_id case-folded
+64  when normalized full query equals normalized remote tool name
```

Candidates with score `0` are omitted. Results sort by descending score and then ascending
case-sensitive `canonical_tool_id`. Return at most the validated limit. There is no fallback
ranking, substring search, stemming, BM25 dependency, typo correction, semantic reranking, or
automatic second query.

### 9.4 Result contract

The ToolResult contains deterministic canonical JSON with:

```json
{
  "result_count": 1,
  "tools": [
    {
      "canonical_tool_id": "mcp__server__tool",
      "server_id": "server",
      "remote_tool_name": "tool",
      "description": "...",
      "input_schema": {"type": "object"}
    }
  ]
}
```

JSON uses `ensure_ascii=False`, `sort_keys=True`, and compact separators. Results do not include
annotations, raw MCP responses, protocol metadata, connection data, configuration, credentials,
or runtime binding objects. The result enters the ordinary post-tool hooks, Artifact persistence,
and 12K ToolResult admission path. No special search-result truncation or Context retention rule
is added.

### 9.5 Requirements

- **MCPV2-SEARCH-001**: `mcp_tool_search` MUST implement the exact schema, validation,
  normalization, fields, score, tie-break, default limit, and maximum limit in section 9.
- **MCPV2-SEARCH-002**: Search MUST be purely local over the immutable catalog and MUST NOT cause
  MCP I/O, registry mutation, base-tool mutation, or catalog mutation.
- **MCPV2-SEARCH-003**: Search results MUST use only the exact bounded fields and canonical JSON
  representation in section 9.4.
- **MCPV2-SEARCH-004**: Search ToolResults MUST use the existing hooks, Artifact path, and CMV3
  admission without an MCP-specific projection or persistence path.
- **MCPV2-SEARCH-005**: Search MUST NOT use dependencies, embeddings, LLM calls, dynamic tuning,
  fallback ranking, or retry.

## 10. MCP Call Gateway

### 10.1 Direct tool contract

The direct Harness tool is named `mcp_tool_call`. Its exact schema is:

```json
{
  "type": "object",
  "properties": {
    "tool": {"type": "string", "minLength": 1},
    "arguments": {"type": "object"}
  },
  "required": ["tool", "arguments"],
  "additionalProperties": false
}
```

The gateway validates only that the argument object has exactly these keys, `tool` is a non-empty
string, and `arguments` is an object. It resolves `tool` by exact case-sensitive
`canonical_tool_id`. An unknown identifier returns one actionable validation error and performs
no remote call.

It does not infer a tool from text, accept raw server/name pairs, coerce arguments, validate the
remote schema, repair malformed arguments, resolve aliases, or select the nearest match. The
remote MCP server remains authoritative for remote argument validation.

### 10.2 Execution

The catalog entry retains the existing thin `MCPTool` binding. `mcp_tool_call` delegates operation
classification and invocation to that exact binding. The binding invokes only:

```text
MCPRuntime.call_tool(server_id, remote_tool_name, arguments)
```

The model-facing gateway is executed once by the existing `ToolExecutor`. It does not invoke a
second executor or manually replay hooks. Existing pre-tool validation, Plan availability,
Permission gate, remote call, post-tool hooks, redaction, Artifact persistence, tracking, and
CMV3 admission therefore occur exactly once.

### 10.3 Requirements

- **MCPV2-CALL-001**: `mcp_tool_call` MUST implement the exact schema and minimal host validation
  in section 10.1.
- **MCPV2-CALL-002**: Canonical lookup MUST be exact and case-sensitive; aliases, fuzzy lookup,
  argument repair, coercion, and automatic search are forbidden.
- **MCPV2-CALL-003**: The gateway MUST delegate to the catalog's existing `MCPTool` binding and
  call the exact raw server/tool identity once.
- **MCPV2-CALL-004**: The gateway MUST execute through `ToolExecutor` exactly once; a gateway
  executor, permission layer, hook path, or result pipeline is forbidden.
- **MCPV2-CALL-005**: Search is not a prerequisite enforced by Runtime. A model can call an exact
  known canonical identity directly, and Runtime neither guesses nor remembers a per-model
  loaded-tool set.
- **MCPV2-CALL-006**: A successful or failed call MUST NOT change direct schemas, catalog
  membership, or another remote tool's exposure.

## 11. Plan and Permission Contract

### 11.1 Frozen phase exposure

| Existing lifecycle state | `mcp_tool_search` | `mcp_tool_call` | Individual remote schemas |
|---|---:|---:|---:|
| Plan policy OFF / direct execution | DIRECT | DIRECT | DEFERRED |
| Auto undecided / planning | DIRECT | HIDDEN | DEFERRED |
| Awaiting approval | HIDDEN | HIDDEN | HIDDEN |
| Approved executing | DIRECT | DIRECT | DEFERRED |
| Completed / cancelled | HIDDEN | HIDDEN | HIDDEN |

Planning search is safe because it inspects only the immutable local catalog. It does not grant
the ability to perform an external MCP call. `mcp_tool_search` is added to the existing
`READ_ONLY_INSPECTION_TOOLS`. No other Plan transition, action, scheduler, or capability policy
changes.

The Planning-to-Executing transition changes the MCP contribution by exactly one direct schema:
`mcp_tool_call`. It never adds all remote schemas. Existing native lifecycle schema changes remain
governed by the runtime-economics specification.

- **MCPV2-PLAN-001**: Planning and undecided phases MUST expose local `mcp_tool_search` and MUST
  hide `mcp_tool_call`.
- **MCPV2-PLAN-002**: Direct and approved executing phases MUST expose both fixed gateways and
  MUST expose zero individual remote schemas.
- **MCPV2-PLAN-003**: Awaiting, completed, and cancelled phases MUST hide both gateways; Completed
  MUST continue exposing zero tools.
- **MCPV2-PLAN-004**: V2 MUST modify no Plan phase, transition, approval rule, update-plan action,
  or execution scheduler.

### 11.2 Permission

Search uses the local read-only operation in section 9.1. A real call uses the existing binding's
conservative classification:

```text
kind: mcp.call
action: <remote_tool_name>
subject: <server_id>/<remote_tool_name>
scope_key: mcp:<server_id>:<remote_tool_name>
is_read_only: false
is_destructive: false
is_sensitive: true
terminal_on_deny: false
```

- **MCPV2-PERM-001**: Every remote invocation MUST pass through the existing Permission gate with
  the exact per-tool conservative scope above before MCP I/O.
- **MCPV2-PERM-002**: Permission denial MUST perform no remote call and MUST retain existing
  recoverable, non-terminal semantics.
- **MCPV2-PERM-003**: Search results, schemas, descriptions, titles, and annotations MUST NOT
  weaken or bypass permission classification.
- **MCPV2-PERM-004**: `PermissionGate`, Permission modes, approval storage, and protected-path
  rules MUST NOT change for V2.

## 12. Result and Failure Semantics

Existing `MCPTool` result conversion remains authoritative:

- ordered text blocks are newline-joined;
- structured content uses canonical compact sorted JSON and the existing marker when combined
  with text;
- any unsupported image, audio, resource link, embedded resource, or unknown content fails the
  whole result without exposing payload;
- `is_error`, SDK timeout, transport/protocol, input-required, empty, serialization, and closed
  runtime cases become one bounded failed ToolResult;
- no call automatically retries, reconnects, restarts, switches transport, or changes health;
- a later explicit model call uses the same owned SDK Client and succeeds or fails normally.

Search failure is limited to validation or local serialization failure. Call-gateway validation
failure performs no remote call. Startup config errors remain runner-construction errors;
connect/discovery/name/schema/collision/catalog/gateway errors remain AgentContext-time startup
failures before Provider use and clean all partial resources atomically.

- **MCPV2-RES-001**: Existing v1 MCP text/structured conversion, unsupported-content rejection,
  safe metadata, and error categorization MUST remain unchanged.
- **MCPV2-RES-002**: Search and call gateway results MUST enter the normal ToolResult path and
  MUST NOT truncate, persist, project, or append themselves.
- **MCPV2-ERR-001**: Catalog/gateway startup failure MUST commit neither the catalog nor either
  gateway and MUST close all partial MCP resources before propagating.
- **MCPV2-ERR-002**: Remote errors MUST produce one ordinary failed ToolResult with no retry,
  reconnect, restart, adapter removal, or health state.
- **MCPV2-ERR-003**: Invalid gateway arguments or an unknown canonical identity MUST return one
  actionable validation failure and MUST NOT be silently repaired.

## 13. Prefix-Cache and Schema Stability Contract

The stable Provider-visible MCP surface is bounded by constants, not remote catalog size:

- Planning/undecided MCP contribution: one schema (`mcp_tool_search`);
- direct/executing MCP contribution: two schemas (`mcp_tool_search`, `mcp_tool_call`);
- awaiting/completed/cancelled MCP contribution: zero schemas;
- individual remote schema contribution: always zero.

The existing `ToolRegistry` insertion order and deterministic schema serialization remain the
base representation. Neither search nor call registers, removes, reorders, or changes a tool.

- **MCPV2-CACHE-001**: Within a stable Plan phase, the complete base Provider-visible tool array
  MUST be byte-for-byte deterministic.
- **MCPV2-CACHE-002**: MCP search MUST NOT mutate or replace the base Provider-visible tool array.
- **MCPV2-CACHE-003**: Calling one MCP tool MUST NOT make it or any unrelated remote schema direct.
- **MCPV2-CACHE-004**: MCP selection MUST NOT use per-turn visibility rewriting, LRU, TTL,
  prediction, or dynamic unloading.
- **MCPV2-CACHE-005**: The same-turn continuation following search or call MUST serialize the
  exact same base tools representation as the request that issued the tool call.
- **MCPV2-CACHE-006**: Planning-to-Executing MUST change the MCP contribution from the fixed search
  gateway to the fixed search-and-call pair; it MUST NOT add N discovered schemas.
- **MCPV2-CACHE-007**: Direct MCP schema bytes and direct MCP schema count MUST be constant for a
  phase across catalogs of 5, 25, and 100 valid remote tools.

These requirements establish prefix structural stability. They do not claim a Provider cache hit
or control Provider-side eviction.

## 14. Observability

No MCP metrics subsystem is added.

- Existing request `plan_phase` records lifecycle phase.
- Existing request `tool_schema_count` is the authoritative direct Provider tool count; no
  duplicate `direct_tool_count` field is added.
- Existing cost tracking `tools_hash` remains the authoritative direct schema fingerprint.
- Startup replaces per-server `exposed_tool_names` with safe counts and emits exactly one
  `mcp_catalog_ready` event containing `registered_mcp_tool_count` and
  `searchable_mcp_tool_count`.
- The search ToolResult metadata contains `mcp_search_query` and `mcp_search_result_count`; the
  existing post-tool trace records these only after normal redaction. It does not record returned
  schemas.
- Existing remote call trace and ToolResult metadata continue recording server id, remote name,
  duration, success, and error kind without config or payloads.

- **MCPV2-OBS-001**: Existing `plan_phase`, `tool_schema_count`, and `tools_hash` MUST remain the
  phase, direct-surface count, and direct-surface fingerprint used by cache regression tests.
- **MCPV2-OBS-002**: Startup MUST emit exactly one `mcp_catalog_ready` event with registered and
  searchable MCP counts and without schemas, config, commands, URLs, or credentials.
- **MCPV2-OBS-003**: Search ToolResult metadata MUST contain only the bounded query and result
  count as MCP search facts; existing redaction MUST run before trace visibility, and returned
  schema bodies MUST NOT be duplicated into trace events.
- **MCPV2-OBS-004**: V2 MUST NOT add a metrics registry, per-tool cache statistics, report
  subsystem, or duplicate tool-call event stream.
